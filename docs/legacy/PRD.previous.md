# y3gym 제품 요구사항 정의서

작성일: 2026-10-09 · 버전: 1.0 · 용도: 기존 프로젝트 정리 및 새 프로젝트의 요구사항 기준

> 사용자는 현재 결과물에 만족하지 않아 기존 개발과 실행을 중단하고 새로 시작하기로 했다. 이 문서는 대화에서 확정한 제품 요구, 기존 구현에서 선택한 운영 정책, 새 프로젝트에서 다시 결정할 사항을 구분한다. 기존 디자인·코드·기술 스택을 그대로 재사용하라는 지시가 아니며, 문서 작성 자체가 새 구현·배포 승인은 아니다.

## 1. 제품 개요

**헬스장 브랜드·지점·시설·트레이너를 소개하고, 방문자를 지점별 전화 또는 카카오톡 문의로 연결하는 공식 홈페이지**를 만든다. 운영자는 개발자 도움 없이 정해진 화면의 콘텐츠를 관리한다.

현재 본점은 한 곳이다. 향후 지점이 늘어도 화면 코드를 수정하거나 같은 정보를 중복 등록하지 않고 운영할 수 있어야 한다. PT 운영관리 프로젝트와는 완전히 별개인 제품이다.

### 목표와 완료 판단

| 목표 | 완료 판단 |
|---|---|
| 방문자가 헬스장의 특징과 신뢰할 만한 정보를 파악한다 | 소개·시설·트레이너·이용안내를 PC와 모바일에서 읽을 수 있다 |
| 원하는 지점에 쉽게 문의한다 | 지점 선택부터 해당 지점의 전화/카카오톡 연결까지 막힘이 없다 |
| 운영자가 콘텐츠를 직접 관리한다 | 소개 수정, 지점/트레이너 관리, 글 작성·미리보기·공개, 팝업 기간 설정을 실제 관리자에서 수행한다 |
| 미완성 수정이 고객에게 보이지 않는다 | 게시글 초안과 공개본이 분리되고 미공개 콘텐츠·이미지 접근이 차단된다 |
| 시각적 완성도를 먼저 확보한다 | PC·모바일 실제 화면과 동작을 검토하고 사용자가 디자인을 승인한다 |

방문자 수·전환율·매출 등의 수치 목표와 분석 도구 도입은 아직 정하지 않았다. 임의의 숫자나 추적 서비스를 요구사항으로 추가하지 않는다.

## 2. 사용자와 주요 흐름

| 사용자 | 목적 | 대표 흐름 |
|---|---|---|
| 처음 방문한 고객 | 분위기·시설·위치·운영시간 파악 | 홈 → 지점 안내 → 시설/이용안내 → 전화 또는 카카오톡 |
| 트레이너를 살펴보는 고객 | 소속·소개·약력 확인 | 트레이너 소개 → 지점별 프로필 → 해당 지점 문의 |
| 공지·이벤트를 확인하는 고객 | 최신 소식과 행사 내용 확인 | 목록 또는 팝업 → 공개 게시글 상세 |
| 콘텐츠 운영자 | 정해진 영역의 정보 관리 | 관리자 로그인 → 콘텐츠 편집 → 저장 또는 초안/미리보기/공개 |
| 시스템 관리자 | 계정·권한·설정·복구 관리 | 일반 콘텐츠 편집과 구분된 제한된 유지보수 |

고객 회원가입·로그인은 없다. 관리자 인증은 필요하다.

## 3. 범위

### 포함

- 브랜드 소개와 고정 구조의 홈 화면.
- 다지점 등록, 본점 지정, 지점별 시설 사진·이용안내·위치·연락처.
- 한 지점에 소속된 트레이너 프로필과 약력.
- 전체 지점 공통 공지·이벤트, 익숙한 글쓰기 편집기.
- 게시글 초안 저장·인증된 미리보기·공개·공개 철회.
- 게시글에 연결되는 기간제 **별도 브라우저 창 팝업**.
- 운영자 콘텐츠 관리, 이미지 업로드·선택·표시 순서 관리.
- PC·모바일 반응형, 모바일 햄버거 메뉴, 절제된 스크롤 등장 효과.
- 향후 고객용 프론트엔드 분리에 대응할 공개 콘텐츠 조회 경계.

### 제외

- 가격·요금표 공개, 결제·쇼핑·회원권 구매.
- PT 관리 서비스 연계, 수업·예약·출결·고객 계정 관리.
- 자체 상담 접수 폼·고객정보 수집 시스템.
- 지점별 게시판, 댓글·좋아요·태그·소셜 기능.
- 자유 페이지 빌더, 운영자의 섹션 자유 추가·삭제·재배치.
- 별도 관리자 프론트 서비스, 불필요한 운영 서비스.
- 게시글 예약 발행·다단계 승인 등 별도 요청이 없었던 확장 기능.

가격 비공개는 전용 필드를 만들지 않는 데 그치지 않는다. 게시글·이미지·팝업 등 공개 자료도 운영자가 검수한다. 자동 OCR·가격 판별 기능은 요구하지 않는다.

## 4. 공개 화면 구성

경로와 세부 배치는 새 설계에서 조정할 수 있다. 아래는 필요한 화면과 역할이며 기존 URL을 그대로 유지할 의무는 없다.

| 화면 | 필요한 내용과 동작 |
|---|---|
| 홈 | 브랜드/로고, 대표 사진·핵심 문구, 소개, 공개 지점 미리보기, 트레이너 안내, 최근 공개 글, 지점별 문의 |
| 지점 안내 | 지점명·본점 표시·소개·대표/시설 사진, 주소·지도, 운영시간·휴무·주차·이용안내, 전화/카카오톡, 소속 트레이너 연결 |
| 트레이너 소개 | 지점별 프로필 묶음, 사진·이름·선택 직급·한줄소개·약력, 해당 지점 안내/문의 연결 |
| 공지·이벤트 목록 | 전체/공지/이벤트 구분, 공개 글 제목·분류·공개일·선택 대표 이미지, 페이지 이동과 빈 상태 |
| 게시글 상세 | 공개 제목·분류·본문·서식·본문 이미지·선택 대표 이미지, 목록 및 지점 안내로 이동 |
| 팝업 창 | 제목·문구·선택 이미지·연결 글 보기, 닫기·오늘 하루 보지 않기 |
| 관리자 | 브랜드, 지점/시설, 트레이너/약력, 공지·이벤트, 팝업, 이미지 관리 |

공통 메뉴는 홈·지점 안내·트레이너 소개·공지/이벤트와 문의 동선으로 구성한다. 별도 상담 접수 페이지를 만들 필요는 없다. 지점 한 곳이면 불필요한 선택 단계를 줄이고, 여러 곳이면 선택한 지점의 연락처로 연결한다. 공통 문의 버튼을 설명 없이 본점 번호로 연결하지 않는다.

## 5. 기능 요구사항

### FR-01. 브랜드와 홈

- 브랜드명·로고·대표 사진·소개 제목/문구·소개 사진을 관리한다.
- 홈의 지점·최근 글은 해당 원본 콘텐츠에서 자동 구성한다. 홈 전용으로 같은 지점/글을 재등록하지 않는다.
- 콘텐츠가 없는 선택 영역은 빈 카드나 가짜 정보를 노출하지 않는다.
- 운영자는 콘텐츠를 편집하며 메뉴·레이아웃 코드나 임의 HTML을 관리하지 않는다.

### FR-02. 지점과 시설·이용안내

- 본점과 지점은 동일한 구조를 사용하고 한 지점을 본점으로 지정한다.
- 지점명, 짧은 소개, 대표 사진, 주소/상세주소, 전화/카카오톡, 운영시간·휴무·주차·기타 이용안내를 관리한다.
- 시설 사진은 여러 장을 등록하고 지점 안에서 순서를 바꿀 수 있다. 사진 설명·대체 설명을 관리한다.
- 공개 여부와 표시 순서를 관리한다. 비공개 지점은 홈·지점 안내·트레이너 섹션 등 고객 화면에서 제외된다.
- 지점 공개·수정이 관련 공개 화면에 같은 원본 데이터로 반영된다.
- 지점 필드와 사진 배치를 함께 저장하며 오류 시 일부만 반영되지 않는다.
- 기존 구현은 모든 지점을 한 페이지의 섹션으로 표시한다. 새 프로젝트의 상세 페이지/탐색 방식은 콘텐츠 규모와 시안에서 결정한다.

### FR-03. 지도와 문의

- 방문자는 지점 주소와 위치를 확인하고 해당 지점의 전화 또는 카카오톡으로 문의할 수 있다.
- 전화는 읽고 복사할 수 있는 텍스트와 연결 버튼을 함께 제공한다. 없는 연락 채널의 버튼은 표시하지 않는다.
- 최신 구현 방향은 **Google 지도 공유의 ‘지도 퍼가기’ 코드/URL을 지점에 등록하는 방식**이다. 초기 네이버 API 선택은 후속 Google 전환으로 대체됐다.
- 운영자는 등록한 지도와 실제 지점 주소가 일치하는지 직접 확인한다. 기본주소나 지도 URL 변경 시 확인을 다시 요구한다.
- 임의 iframe/스크립트를 실행하지 않고 허용된 지도 URL만 처리한다.
- 기존 구현은 외부 연결 안내와 지도 보기 클릭 후 iframe을 로드한다. 지도 실패·미등록 상태에서도 주소·연락처는 이용 가능해야 한다.
- 주소 자동검색·자동 좌표 추출이나 ‘모든 Google 지도 API는 키 없이 무료’라는 가정을 요구하지 않는다. 선택 방식의 실제 위치·동작·현행 제공 조건은 출시 전에 확인한다.

### FR-04. 트레이너

- 트레이너 한 명은 정확히 한 지점에 소속된다.
- 이름, 소속 지점, 프로필 사진, 한줄소개, 직급, 약력을 관리한다.
- 직급은 선택 자유 텍스트다. 미입력 시 숨기며 권한·자동 정렬·별도 관리 메뉴와 연결하지 않는다.
- 약력은 학력·수상·자격증·경력으로 구분하며 항목 추가·수정·삭제·순서 조정이 가능하다. 빈 분류는 숨긴다.
- 프로필과 소속 지점이 모두 공개일 때만 노출한다. 지점 비공개가 트레이너 원본 데이터를 삭제하거나 자체 공개 설정을 바꾸지는 않는다.
- 지점 이동은 같은 트레이너의 소속 변경으로 처리한다. 사진/약력과 프로필을 복제하지 않는다.
- 프로필과 약력은 하나의 편집 단위로 저장한다.

### FR-05. 공지·이벤트와 글쓰기

- 전체 홈페이지 공통 콘텐츠이며 지점별 소유권을 붙이지 않는다.
- 제목, 공지/이벤트 분류, 선택 대표 이미지, 본문을 관리한다.
- **일반 게시판·문서 작성처럼 한 본문에서 문단을 이어 쓰는 편집 경험**을 제공한다. 문단마다 별도 블록을 추가·펼치는 과정을 기본 글쓰기 흐름으로 강요하지 않는다.
- 한글 입력, 줄바꿈/문단, 굵게·기울임·링크, 본문 이미지 삽입·교체를 쉽게 수행한다. 대표 이미지와 본문 이미지는 역할과 입력 위치가 명확히 구분된다.
- 새 글 초안은 공개 목록/상세에 나타나지 않는다.
- 기존 공개 글을 수정해 초안 저장해도 공개 제목·본문·이미지·공개 시각·팝업이 참조하는 글 제목은 유지된다.
- 권한 있는 운영자는 수정 초안을 미리 보고, 명시적으로 공개한 뒤에만 고객 화면에 반영한다.
- 공개 철회 시 목록·상세·연결 팝업에서 제외한다. 과거 버전 복원을 제공하면 먼저 초안으로 복원하고 별도 공개한다.
- HTML과 공개 API는 같은 공개본을 제공한다. 관리자 로그인 상태로 공개 URL에 접근해도 초안이 섞이지 않는다.

### FR-06. 기간제 팝업

- **일반 본문 카드나 페이지 위 레이어가 아니라 별도 브라우저 창을 요청하는 형태**다. 이는 사용자가 명시적으로 정정한 요구사항이다.
- 모든 팝업은 게시글 하나에 연결해야 한다. 게시글마다 팝업을 반드시 만들어야 하는 것은 아니다.
- 제목·문구·선택 이미지·사용 여부·시작/종료 일시를 관리한다. 팝업 활성화와 게시글 공개는 별도 동작이다.
- 연결 글이 공개이고 팝업이 활성 상태이며 `시작 <= 서버 현재 시각 < 종료`일 때만 노출한다. 입력·운영 기준 시간대는 한국 시간이다.
- 팝업 종료/비활성화가 연결 글을 비공개로 만들지는 않는다. 연결 글을 비공개로 바꾸면 팝업도 노출 대상에서 제외한다.
- 닫기와 ‘오늘 하루 보지 않기’를 제공한다. 오늘 숨김은 팝업별로 한국 시간 다음 날 00:00까지 유지한다.
- 자동 새 창이 차단되면 사용자가 전용 버튼을 눌러 열 수 있어야 한다. 브라우저에 따라 새 탭으로 처리될 수 있으므로 모든 기기에서 같은 창 모양·위치를 보장하지 않는다.
- 창 열기/내용 로딩 실패를 ‘이미 표시됨’으로 처리하지 않는다. 연속 클릭으로 창이 계속 늘어나거나 자동 시도를 반복하지 않는다.
- 직접 팝업 URL에 접근해도 서버의 기간·공개 조건을 적용한다.
- 기존 구현의 글당 최대 1개, 홈에서 우선순위 첫 후보만 자동 표시, 탭 세션당 1회 규칙은 §7의 재검토 가능한 운영 기본값이다.

### FR-07. 관리자와 미디어

- 운영자는 고정 구조 안에서 콘텐츠를 관리하며 자유 페이지 빌더는 사용하지 않는다.
- 저장, 초안 저장, 미리보기, 공개, 비공개/비활성화를 혼동하지 않도록 안내한다. 모델별 반영 시점이 다르면 명확히 표시한다.
- 필수값·입력 오류·다른 운영자의 선행 저장 충돌을 이해하기 쉬운 메시지로 안내하고 기존 내용을 보호한다.
- 이미지 업로드·선택·썸네일·본문 삽입 흐름을 실제 브라우저에서 확인한다.
- 초안 전용 이미지·원본·관리자 썸네일은 URL을 알아도 무권한으로 접근할 수 없어야 한다.
- 기존 공개 이미지 파일을 덮어써서 공개 글이 몰래 달라지지 않도록 새 이미지 등록 후 참조를 변경한다.
- 공유 이미지는 현재 공개 사용처가 하나라도 있을 때 표시될 수 있다. 마지막 공개 사용처가 없어지면 이후 무권한 요청을 차단한다. 이미 내려받은 복사본의 회수는 보장하지 않는다.

## 6. 콘텐츠 관계

기술 중립적 개념 모델이다. 정확한 DB 테이블·필드 길이·CMS 클래스·API DTO를 확정하는 표가 아니다.

| 개념 | 핵심 내용 | 관계 |

## 7. 기존 운영 정책과 새 프로젝트의 결정 구분

아래는 이전 단계에서 한정 채택하여 구현한 정책이다. 사용자 고유 요구와 기술적 선택을 혼동하지 않도록 별도로 적는다. 새 프로젝트의 권장 출발점으로 검토하되 변경 시 영향과 이유를 기록한다. 기존 ADR의 Proposed 전체를 이 문서로 Accepted로 바꾸지 않는다.

| 항목 | 기존 구현의 기준 | 새 설계 시 유의점 |

## 8. 디자인·사용성 요구

### 방향

- 최신 사용자 지정 레퍼런스는 [승종 홈페이지](https://www.seungjong.co.kr/)다. 초기 BRO Fitness 참고안은 현재 주 레퍼런스가 아니다.
- 레퍼런스의 타이포그래피·여백·사진과 텍스트의 균형·PC/모바일 탐색·스크롤 등장 경험을 참고한다. 로고·사진·문구·전체 배치를 그대로 복제하지 않고 헬스장 콘텐츠에 맞춰 설계한다.
- 사용자는 레퍼런스의 폰트를 따르길 요청했다. 기존 결과는 제목 IBM Plex Sans KR·본문 SUIT를 사용했지만, 새 디자인이 이 조합을 확정적으로 승계하는 것은 아니다. 사용 가능한 폰트와 실제 한글 화면을 비교해 정한다.
- 하늘색 선호가 있었으나 화면과 버튼 전반을 하늘색으로 채우는 결과는 거부됐다. 밝은 중립 배경·짙은 본문색에 포인트색을 제한하고, 버튼은 위치·배경·중요도에 맞춘다. 정확한 색상값은 새 시안에서 결정한다.
- 지금 구현된 화면은 새 프로젝트의 디자인 승인 기준으로 사용하지 않는다.

### 반드시 확인할 동작

- PC는 로고와 메뉴·문의 버튼이 의도한 위치에 안정적으로 정렬된다. 모바일 변경이 PC 메뉴를 한쪽으로 몰거나 줄바꿈시키지 않는다.
- 모바일은 눈에 잘 보이고 누르기 쉬운 햄버거 버튼으로 메뉴를 연다. 닫기, 메뉴 선택, 키보드 이동, 화면 폭 변경 시에도 정상 동작한다.
- 지점 영역 등 일반 콘텐츠를 마우스로 클릭했을 때 불필요한 큰 테두리가 생기지 않는다. 키보드 사용자를 위한 버튼/링크의 포커스 표시는 유지한다.
- 스크롤 등장 효과는 짧고 절제되게 적용한다. 모션 감소 설정·JavaScript 실패·키보드 접근에서도 내용이 사라지지 않는다.
- 긴 한글 제목, 사진 없음, 지점 1개/여러 개, 좁은 화면, 확대 상태에서도 잘림·겹침·가로 넘침이 없어야 한다.
- CSS/JS 변경 후 기존 캐시가 남은 일반 새로고침에서도 새 HTML과 충돌하지 않아야 한다.

**디자인 작업 순서:** PC·모바일 대표 시안 → 사용자 방향 확인 → 실제 구현/브라우저 검수 → 사용자 결과 확인 → Git 검토. 기존의 ‘테스트가 통과했으므로 디자인도 완료’ 판단을 반복하지 않는다.

아래 수치는 새 검수의 제안 기준이며 기존 전체 제품이 이미 통과했다는 뜻은 아니다.

검증 결과는 서버 단위/통합 검사, 브라우저 자동 실행, 사용자 수동 확인, 실제 운영 검증으로 구분한다. HTTP 200이나 모의 DOM 검사는 실제 화면 확인을 대체하지 않는다. Headless 새 페이지 생성은 사용자의 OS 창 표시·브라우저 차단 정책 확인과 구분한다.

## 10. 기술·배포 제약

- 기존 구현: Django + Wagtail + PostgreSQL, 서버 템플릿과 공개 JSON API, CSS/JavaScript, 제품과 SPIKE를 분리한 로컬 실행.
- **새 프로젝트 기술 스택은 재선정 가능**하다. 현재 CMS·필드명·템플릿·잠금 코드·패키지 버전을 제품 요구사항으로 고정하지 않는다. 선택안은 편집 경험·유지보수·이미지/초안 보호·운영비를 함께 비교한다.
- 향후 고객 프론트엔드와 백엔드를 분리해도 같은 공개 규칙을 사용할 수 있어야 한다. 처음부터 별도 관리자 앱까지 만들지는 않는다.
- 현재 개발 실행 기준은 Windows 호스트 위 WSL Ubuntu이며 상용 배포는 Linux를 대상으로 논의해 왔다. 환경 변경이 필요하면 별도 결정한다.
- 도메인은 구매 예정, 호스팅·예산·배포 대상은 미정이다. 무료 호스팅 선호는 있으나 무료 운영이 보장된 것은 아니다.
- 정적 프론트 호스팅만으로 관리자·DB·업로드 저장·초안/기간 판정 운영이 모두 해결된다고 가정하지 않는다. 새 아키텍처와 함께 비용·영속성·백업·중단 조건을 확인한다.
- 운영은 HTTPS, 비밀값 분리, 비공개 미디어 보호, 백업/복원, 로그·운영 책임, 롤백 계획을 준비한다. 대상과 비용을 구체적으로 검토하고 별도 승인 후 배포한다.

| 호스팅·예산·도메인·운영 책임 | 미정 | 배포 준비 단계 |
| 보존/유지보수 삭제·백업 목표 | 기존 제한 정책과 로컬 실험만 있음 | 운영 설계 시 |

실제 자료가 없다는 이유로 디자인·기본 기능 검토를 전부 막지 않는다. 임시 자료는 임시임을 명시하고 실제 인물의 이력이나 영업 정보를 꾸며내지 않는다. 사용자만 결정할 정보가 필요한 시점에 한 번 묶어 요청한다.

## 12. 새 프로젝트의 권장 진행 순서

1. 이 PRD에서 유지할 요구와 변경할 정책을 확인하고 새로운 작업 위치·기술 설계를 정한다. 기존 저장소/DB를 초기화하지 않는다.
2. 대표 콘텐츠를 갖춘 PC·모바일 홈, 지점 화면, 메뉴, 팝업 시안을 먼저 검토한다. 글쓰기 편집 흐름도 작은 시제품으로 확인한다.
3. 사용자 디자인 방향 확인 후 사이트/지점/트레이너/글/팝업/지도 기능을 작게 나눠 구현한다.
4. 각 단위에서 서버·실제 브라우저 검증을 수행하고, 디자인은 사용자 확인 후 Git 검토로 넘긴다.
5. 실제 콘텐츠·지도·권한·미디어·배포/복구를 최종 검수한 뒤 별도 승인으로 공개한다.

새 프로젝트 자동 개발은 아직 시작하지 않는다. 사용자 확인 대기 중 예약 실행은 중지하고 같은 확인 요청을 반복하지 않는다.

## 13. 기존 프로젝트 인수인계 상태

- 기존 제품은 기본 콘텐츠·지점·트레이너·공지/이벤트·팝업·Google 지도 입력·공개 HTML/API를 구현한 상태다. 요구사항 검증과 출시 완료는 구분해야 한다.
- 관리자 글쓰기·공개 화면 일부는 사용자 수동 정상 보고가 있고 서버/브라우저 검증 기록이 있다. 전체 관리자·실물 모바일·실제 지도·상용 배포가 모두 검증된 상태는 아니다.
- 모바일 메뉴 보완 DEV-06-I까지 Git 완료 기록이 있다. 마지막 별도 창 팝업 DEV-06-J는 로컬 구현·검증 후 사용자 디자인 승인 전이며 미커밋으로 보존한다. 이번 개발 중단을 디자인 승인으로 해석하지 않는다.
- 기존 코드·문서·Git 기록·DB·계정·사진·초안/리비전은 참고 자료로 보존한다. 새 프로젝트로 자동 복사·데이터 이관·삭제하지 않는다.
- 기존 개발 실행 종료의 실제 결과는 [현재 작업 기록](tasks/current.md)의 2026-10-09 중단 기록을 따른다. 과거 README/검증 보고서의 실행 PID·유지 문구는 당시 이력이다.
