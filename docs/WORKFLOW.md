## 한 단위의 순차 진행

1. **설계 지시:** 사용자와 확정한 요구·범위·완료 기준을 바탕으로 다음 작은 단위를 정한다. 대상, 허용 변경, 보존할 기존 변경, 검사 범위, 미결정 사항과 종속 작업을 명시해 개발에 지시한다.
2. **개발·보고:** 개발은 실제 파일을 확인하고 구현·문서 갱신·자체 검사를 수행한다. 이번 변경 파일과 차이, 실제 실행 명령·결과, 실패·미검증·남은 문제를 최종 보고한다.
3. **개발 보고 검토:** 설계는 파일·명령·결과·미검증 범위를 완료 기준과 대조한다. 이상이 있으면 개발에 재지시하거나 사용자와 설계를 논의한다. 보고에 이상이 없으면 해당 변경과 완료 기준을 테스트에 전달한다.
4. **독립 검증·보고:** 테스트는 필요한 검사를 직접 수행하고 재현 조건·결과·근거·한계를 보고한다. 과거 결과를 읽은 것과 이번에 재실행한 검사를 구분하고, 코드 수정이 필요하면 설계에 보고한다. 공유 디렉터리의 기존 콘텐츠·검수 이력을 불필요하게 덮어쓰지 않는다.
5. **검증 보고 검토·반복:** 설계는 이상이 있으면 개발 수정과 필요한 재검증을 지시하거나 사용자와 설계를 수정한다. 보고에 이상이 없고 다음 단위의 진행 조건이 충족되면 승인된 계획의 다음 작은 단위를 자동 진행한다. 필요한 시점에 아래 Git 절차를 수행한다.

개발·테스트·Git 결과는 각 담당 세션의 최종 보고로 제출하고 설계가 읽어 다음 담당에 지시한다. 담당 세션끼리 다음 작업을 직접 넘기지 않는다. 같은 단위의 구현과 독립 검증은 순서대로 진행하며, 공유 파일을 동시에 수정해 서로의 변경을 덮어쓰지 않는다.

## 진행 조건과 승인 경계

- 이미 승인된 범위는 매 단위마다 재확인하지 않는다. 자동 반복 지시는 운영 정책·미검토 설계안을 임의 확정하거나 제품·기술 범위를 확대하는 승인이 아니다.
- 사용자 결정이 필요한 운영 정책·설계 변경, 사용자 시각 승인, 새 비용·배포·외부 변경은 필요한 결정이 오기 전 해당 종속 작업을 멈춘다. 기존 승인으로 진행할 수 있는 독립 작업은 계속한다. 시각 변경은 실제 화면·캡처를 준비해 설계가 사용자 확인을 받는다.
- **구현 완료 / 독립 검증 완료 / 사용자 시각 승인 / Git 반영**을 각각의 근거와 함께 구분해 보고한다. 하나의 완료를 다른 단계의 완료로 확대하지 않는다. 개발 자체 검사와 테스트 담당의 독립 검증도 구분한다.
- PRD·기술 설계 등에 남은 이전 단위의 “이번 단위에서 멈춤”, “M2-1만 진행”은 당시 범위 기록이다. 이번 최신 지시부터 승인된 계획 안의 반복 진행에 이 절차를 적용하되, 기존 검수 기록·캡처·승인 이력을 재작성하지 않는다. 무관한 다음 기능을 자동 시작하지 않는 작업 규칙은 유지한다.

**진행 이력:** WORKFLOW-01 문서 작성 당시 M2-1은 구현돼 있었고 M2-2의 지점 정책 응답을 기다려 기능 구현을 시작하지 않았다. 이후 사용자가 본점 1곳·공개 본점 우선 표시/기본 선택, 미완성 초안 허용·지점명/주소/운영시간 공개 필수, 마지막 공개 지점 철회·0곳 준비 중 안내/문의 숨김을 확정했다. 설계가 WORKFLOW-01 독립 검증 보고를 검토한 뒤 M2-2 구현을 지시했다. 최신 상세 정책과 제외 범위는 [PRD](PRD.md#fr-02-지점시설)·[구현 계획](IMPLEMENTATION-PLAN.md)을 따른다. 깃노예는 같은 루트·local에서 읽기 전용 준비 검토를 맡았으며 개발과 독립 검증 완료 전 Git 반영을 시작하지 않는다.

**현재 상태 — M2-2 종료 문서 정리:** [초기 독립 검증 FAIL](../backend/review/branches-independent/README.md) → [R1 보완·자체 검사](../backend/review/branches-repair/README.md) → [독립 재검증 PASS_WITH_WARNINGS](../backend/review/branches-independent-recheck/README.md). F01·F02·W01 해결·차단 결함 없음을 확인했고 기존 `backend/review/workflow-01/verify.py`의 전역 포맷 경고 1개는 남는다. 초기 FAIL·R1·이전 캡처는 당시 기록으로 보존한다. 이번 종료 작업은 최신 문서·경로/앵커/내용 일치 검사만 수행하며 제품 검사를 재실행하지 않는다. 사용자 시각·관리자 사용성 승인, 실제 기기·Whale·한국어 IME·운영 환경 검증은 완료로 취급하지 않는다.

**다음 진행 조건:** 개발의 종료 문서 보고를 설계가 검토한 뒤 깃노예에 첫 Git 체크포인트를 별도로 지시한다. 이 문서 정리는 commit·push·배포를 수행하지 않는다. 트레이너의 확정 입력 정책은 [FR-03](PRD.md#fr-03-트레이너), 다음 작은 단위는 [M2-3 트레이너 관리](IMPLEMENTATION-PLAN.md#다음-단위-m2-3-트레이너-관리)에 기록했다. **M2-3은 미착수**이며 Git 체크포인트와 설계의 별도 구현 지시 이후 진행한다. 개발이 이번 문서 작업에 이어 자동으로 구현을 시작하지 않는다.

## 필요한 시점의 Git 반영

1. 설계가 이 프로젝트 루트의 깃노예 세션을 생성하고 테스트된 변경, 검증 근거·한계, 반영할 범위를 전달한다. 같은 프로젝트의 담당이 이미 있다면 현재 세션을 확인해 재사용한다.
2. 깃노예는 실제 변경·기존 미커밋 변경·추적/미추적 파일, 현재 브랜치·기존 원격과 테스트된 범위를 대조한다. 검증 이후의 변경이나 다른 작업이 섞여 있으면 임의로 함께 반영하지 않고 설계에 보고한다.
3. 검토에 이상이 없으면 지시한 변경만 커밋하고 기존 원격에 푸시한다. 커밋 메시지는 한글로 구체적으로 작성한다. 커밋 해시·대상 브랜치/원격·실제 푸시 결과·남은 변경을 보고하고 설계가 확인한다.
4. Git 실패, 비밀값, 용량 문제, 의심되는 타인 변경, 검증 누락은 이유와 영향을 보고하고 관련 반영을 멈춘다. 임의 force push·reset·삭제·배포로 해결하지 않는다. 커밋·푸시가 배포 승인이나 배포 완료를 뜻하지 않는다.
