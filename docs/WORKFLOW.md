## 한 단위의 영향 범위에 맞춘 진행

1. **범위 설정:** 요청한 목표와 실제 영향 범위에 맞춰 대상·허용 변경·보존할 기존 변경·완료 기준·필요 검사만 정한다. 관련 없는 미완료 운영 과제를 선행 조건으로 만들지 않는다.
2. **담당 실행:** 소규모 변경은 기본적으로 담당 하나가 구현·관련 검증·보고까지 수행한다. 실제 사용법이나 계약이 바뀐 문서만 수정하며 README·PRD·디자인 문서를 매번 모두 갱신하지 않는다.
3. **필요한 추가 검증:** 전체 회귀·별도 독립 검증은 영향 범위나 사용자 요청으로 필요한 경우에만 수행한다. 별도 담당이 참여하면 구현 보고와 완료 기준을 전달하고, 같은 공유 파일을 동시에 수정하지 않는다. 이미 확인한 같은 상태를 성공 횟수를 늘리기 위해 반복 검사하지 않는다.
4. **보고·종료:** 변경 내용·실제 검증·남은 문제를 간결하게 보고한다. 기존 근거 사용과 이번 실행, 자체 검사와 독립 검증을 구분한다. 실패를 숨기지 않되 원시 로그·캡처·보고서를 대량 생성하지 않는다. 완료 조건을 충족하면 멈추고 후속 마일스톤을 자동으로 시작하지 않는다.

검증 도구가 실패하면 좁은 원인 수정과 재확인까지만 수행한다. 해결되지 않으면 한계와 현재 목표의 차단 여부를 보고하며 도구 전체 개선 작업으로 확대하지 않는다. 별도 담당을 활용할 때는 각 담당이 최종 결과를 설계에 보고하며, 담당끼리 후속 작업을 자동으로 넘기지 않는다.

## 설정 변경과 데이터 보호

- 데이터에 손대지 않는 설정 변경은 변경 설정의 롤백 수단을 준비한다. DB·미디어 전체 백업이나 복구 연습을 자동으로 수행하지 않는다.
- DB 변경·삭제·저장소 이전 등 데이터 위험이 있으면 필요한 보호조치와 추가 범위를 설명하고 승인받는다. 기존 정기 백업·보안 통제·명시적으로 승인된 운영 절차는 임의로 끄지 않는다.
- Caddy 설정만 바꿀 때는 reload 가능 여부를 우선 확인한다. 서비스 중단·컨테이너 재생성이 필요하면 이유와 영향을 먼저 설명한다.
- 원본 데이터·기존 실행 환경을 보존한다. 이번에 만든 미사용 QA 자원만 소유·공유 경계를 확인한 뒤 기존 도구로 정리한다. 상세 절차는 [백엔드 QA 안내](../backend/README.md#qa-환경-생성실행정리)를 따른다.

- 이미 승인된 범위는 매 단위마다 재확인하지 않는다. 기존 승인은 운영 정책·미검토 설계안을 임의 확정하거나 제품·기술 범위를 확대하는 승인이 아니다.

## 필요한 시점의 Git 반영

1. 설계가 이 프로젝트 루트의 깃노예 세션을 생성하고 테스트된 변경, 검증 근거·한계, 반영할 범위를 전달한다. 같은 프로젝트의 담당이 이미 있다면 현재 세션을 확인해 재사용한다.
2. 깃노예는 실제 변경·기존 미커밋 변경·추적/미추적 파일, 현재 브랜치·기존 원격과 테스트된 범위를 대조한다. 검증 이후의 변경이나 다른 작업이 섞여 있으면 임의로 함께 반영하지 않고 설계에 보고한다.
3. 검토에 이상이 없으면 지시한 변경만 커밋하고 기존 원격에 푸시한다. 커밋 메시지는 한글로 구체적으로 작성한다. 커밋 해시·대상 브랜치/원격·실제 푸시 결과·남은 변경을 보고하고 설계가 확인한다.
4. Git 실패, 비밀값, 용량 문제, 의심되는 타인 변경, 검증 누락은 이유와 영향을 보고하고 관련 반영을 멈춘다. 임의 force push·reset·삭제·배포로 해결하지 않는다. 커밋·푸시가 배포 승인이나 배포 완료를 뜻하지 않는다.
